# Testing Strategy & Playwright Guide

This document outlines our testing architecture, explains how Playwright fits into our
tech stack, and provides instructions for running and debugging tests locally
(including CI environment emulation).

---

## What is Playwright and how does it work?

Playwright is a modern end-to-end (E2E) and component testing framework developed by
Microsoft. It controls browser engines (Chromium, WebKit, Firefox) programmatically via
direct browser protocols.

### How it works in our architecture

```
┌────────────────────────────────────────────────────────────────────────┐
│                          Playwright Runner                             │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ HTTP / user actions
                                    ▼
       ┌────────────────────────────────────────────────────────┐
       │                   Vite Dev Server                      │
       │                   (Frontend UI)                        │
       └───────────┬────────────────────────────────┬───────────┘
                   │ /api/v1/*                         │ /_allauth/*
                   ▼                                ▼
       ┌────────────────────────────────────────────────────────┐
       │                 Django REST Backend                    │
       └────────────────────────────┬───────────────────────────┘
                                    │ SQL queries
                                    ▼
       ┌────────────────────────────────────────────────────────┐
       │                     PostgreSQL                         │
       └────────────────────────────────────────────────────────┘
```

- **Headless browser execution** — Playwright opens a real Chromium instance to render
  the frontend, interact with UI components, trigger events, and inspect the resulting
  DOM state.
- **Full-stack execution** — in E2E tests, network requests generated by the React UI
  travel through the Vite proxy layer to Django and persist data in PostgreSQL.

## Test tiers in our pipeline

So far, we use three testing tiers to balance execution speed against safety guarantees:

| Test tier | Scope | Environment requirements | Execution mechanism | CI job |
| --- | --- | --- | --- | --- |
| Backend unit & API | Python functions, Django models, REST endpoints | Clean PostgreSQL container | `uv run pytest` on host | `backend` |
| Frontend component *(planned)* | Isolated React components (states, props, a11y) | Node.js host — no Docker, backend, or DB | `npm run test:components` | `frontend` |
| End-to-end (E2E) | Full user workflows (auth, DB state, navigation) | Docker Compose (backend + postgres + frontend) | `npm run test:e2e` | `e2e` |

> **Note:** the component tier is not implemented yet — there is no `test:components`
> script in [package.json](package.json) and no component-test runner installed. Only the
> backend and E2E tiers currently run.

## Do I need to install Playwright locally?

- **Frontend developers — yes.** Install the browser binaries locally so you can run and
  debug E2E specs, use the Playwright Inspector, and write new tests.
- **Backend-only developers — optional.** If you work strictly on Django endpoints or
  Python business logic, `pytest` is enough. Installing Playwright still lets you verify
  that backend changes don't break core UI workflows before pushing.

### Quick setup

```bash
# Navigate to the frontend workspace
cd frontend

# Install dependencies (if not already installed)
npm install

# Download the Chromium binaries Playwright needs
npx playwright install chromium
```

## Emulating the CI environment locally

Local environments use Caddy (`https://poolaki.localhost`) for HTTPS and routing. In CI,
Caddy and the monitoring services are stripped out and ports are exposed directly —
`http://localhost:5173` for the frontend, `http://localhost:8000` for the backend.

To reproduce the CI setup locally when a test fails on GitHub Actions:

**1. Spin up the CI containers** — use the base compose file plus the
[docker-compose.ci.yml](../docker-compose.ci.yml) override:

```bash
COMPOSE_FILE=docker-compose.yml:docker-compose.ci.yml docker compose up -d --build frontend backend
```

**2. Run database migrations** inside the backend container:

```bash
docker compose exec backend python manage.py migrate
```

**3. Stream container logs** (recommended) in a second terminal, to watch server
responses and debug API failures:

```bash
docker compose logs -f backend frontend
```

**4. Run the E2E suite** against the CI base URL:

```bash
cd frontend
BASE_URL=http://localhost:5173 npx playwright test
```

**5. Tear down** when you're done:

```bash
COMPOSE_FILE=docker-compose.yml:docker-compose.ci.yml docker compose down -v
```

## Debugging tips

Open UI mode for visual, step-by-step inspection:

```bash
npx playwright test --ui
```

Run a single spec:

```bash
npx playwright test tests/auth.spec.ts
```

**Inspect failed artifacts.** Playwright captures screenshots, traces, and an HTML report
on failure — check [test-results/](test-results/) for failure snapshots, or open the
report with `npx playwright show-report`.

**Stay proxy-aware.** Any new backend endpoint (e.g. custom OAuth or auth paths under
`/_allauth`) must be added to `server.proxy` in [vite.config.ts](vite.config.ts), or the
request won't be routed when running without Caddy.
