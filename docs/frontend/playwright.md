# Testing Strategy & Playwright Guide

This document outlines our testing architecture, explains how Playwright fits into our
tech stack, and provides instructions for running and debugging tests locally
(including CI environment emulation).

---

## What is Playwright and how does it work?

Playwright is a modern end-to-end (E2E) and component testing framework developed by
Microsoft. It controls browser engines (Chromium, WebKit, Firefox) programmatically via
direct browser protocols.

### How it works in our architecture

```
┌────────────────────────────────────────────────────────────────────────┐
│                          Playwright Runner                             │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ HTTP / user actions
                                    ▼
       ┌────────────────────────────────────────────────────────┐
       │                   Vite Dev Server                      │
       │                   (Frontend UI)                        │
       └───────────┬────────────────────────────────┬───────────┘
                   │ /api/v1/*                         │ /_allauth/*
                   ▼                                ▼
       ┌────────────────────────────────────────────────────────┐
       │                 Django REST Backend                    │
       └────────────────────────────┬───────────────────────────┘
                                    │ SQL queries
                                    ▼
       ┌────────────────────────────────────────────────────────┐
       │                     PostgreSQL                         │
       └────────────────────────────────────────────────────────┘
```

- **Headless browser execution** — Playwright opens a real Chromium instance to render
  the frontend, interact with UI components, trigger events, and inspect the resulting
  DOM state.
- **Full-stack execution** — in E2E tests, network requests generated by the React UI
  travel through the Vite proxy layer to Django and persist data in PostgreSQL.

## Test tiers in our pipeline

So far, we use three testing tiers to balance execution speed against safety guarantees:

| Test tier | Scope | Environment requirements | Execution mechanism | CI job |
| --- | --- | --- | --- | --- |
| Backend unit & API | Python functions, Django models, REST endpoints | Clean PostgreSQL container | `uv run pytest` on host | `backend` |
| Frontend component *(planned)* | Isolated React components (states, props, a11y) | Node.js host — no Docker, backend, or DB | `npm run test:components` | `frontend` |
| End-to-end (E2E) | Full user workflows (auth, DB state, navigation) | Docker Compose (backend + postgres + frontend) | `npm run test:e2e` | `e2e` |

> **Note:** the component tier is not implemented yet — there is no `test:components`
> script in [package.json](package.json) and no component-test runner installed. Only the
> backend and E2E tiers currently run.

## Do I need to install Playwright locally?

- **Frontend developers — yes.** Install the browser binaries locally so you can run and
  debug E2E specs, use the Playwright Inspector, and write new tests.
- **Backend-only developers — optional.** If you work strictly on Django endpoints or
  Python business logic, `pytest` is enough. Installing Playwright still lets you verify
  that backend changes don't break core UI workflows before pushing.

### Quick setup

```bash
# Navigate to the frontend workspace
cd frontend

# Install dependencies (if not already installed)
npm install

# Download the Chromium binaries Playwright needs
npx playwright install chromium
```

## Goal fixtures - TEMPORARY before the goals API lands

The transaction specs create rows through the real API and need nothing seeded:
every workspace gets its own categories when it is created, and the specs read
them back from `GET /organizations/<org_id>/categories/`.

Goals are the exception. The backend exposes no endpoint for them, so the
frontend still declares them client-side in
[lib/goals.ts](../../frontend/src/lib/goals.ts), and a contribution is rejected
unless a goal with that id exists in the workspace you are in. Seeding is
therefore only needed to try the transaction form's **Saving** tab by hand.

`manage.py` needs the database credentials, which the entrypoint sources from
the Vault agent's files at start-up. An exec'd shell starts *without* them, so
a bare `docker compose exec -T backend python manage.py ...` fails with
`fe_sendauth: no password supplied`. Source the same file first; a small shell
function keeps that out of the way:

```bash
manage() {
  docker compose exec -T backend sh -c \
    "set -a; . /vault/agent/secrets/db-creds.env; set +a; python manage.py $*"
}
```

Goals are scoped to a workspace, so the command takes the one to seed:

```bash
# The number is the workspace id from the URL, /o/<id>
manage seed_transaction_fixtures 1

# Print what it would write and roll back
manage seed_transaction_fixtures 1 --dry-run
```

The command is idempotent: it updates the rows in place, so running it twice is
safe. Note that the goal ids are fixed, so naming a *different* workspace moves
those goals rather than adding more.

> **IMPORTANT:** Named volumes survive `docker compose down` — reseeding is only needed after
> `docker compose down -v`, which drops the database. Drop this step entirely
> once the goals endpoints land.

## Test users and the signup rate limit

allauth allows 20 signups per minute per IP. Every spec used to register its
own users, so a parallel run signed up about a dozen accounts within seconds
and back-to-back runs failed in `beforeAll` on the Sign up page.

The `setup` project ([shared-owner.setup.ts](../../frontend/tests/shared-owner.setup.ts))
now registers one **shared owner** per run and saves the session to
`frontend/playwright/.auth/` (git-ignored). It runs before any spec, including
when you run a single file. Specs open it with `openAsSharedOwner(browser)` from
[helpers.ts](../../frontend/tests/helpers.ts).

Which user to use in a new spec:

| The user... | Use |
|---|---|
| only creates things: workspaces, invitations, transactions | the shared owner |
| is asserted on by per-user state: notification or invitation counts | `registerUser` |
| changes their password or logs out of the shared session | `registerUser` |
| is what the test is about: signup, registration redirects | `registerUser` |

When the shared owner needs data with exact counts, put it in a workspace of
its own (`createWorkspaceViaApi`), not in their personal workspace, which
other specs use at the same time.

## Emulating the CI environment locally

Local environments use Caddy (`https://poolaki.localhost`) for HTTPS and routing. In CI,
Caddy and the monitoring services are stripped out and ports are exposed directly —
`http://localhost:5173` for the frontend, `http://localhost:8000` for the backend.

To reproduce the CI setup locally when a test fails on GitHub Actions:

**1. Spin up the CI containers** — use the base compose file plus the
[docker-compose.ci.yml](../docker-compose.ci.yml) override:

```bash
COMPOSE_FILE=docker-compose.yml:docker-compose.ci.yml docker compose up -d --build frontend backend
```

**2. Migrations** run in the backend entrypoint before `/health/` answers, so
there is nothing to do here. If you ever need `manage.py` by hand, use the
`manage` function from the section above; a bare `docker compose exec` has no
database credentials.

**3. Seed the goals** — optional, and only for trying the **Saving** tab by
hand; the specs need nothing seeded (see the section above):

```bash
# The number is the workspace id from the URL, /o/<id>
manage seed_transaction_fixtures 1
```

**4. Stream container logs** (recommended) in a second terminal, to watch server
responses and debug API failures:

```bash
docker compose logs -f backend frontend
```

**5. Run the E2E suite** against the CI base URL:

```bash
cd frontend
BASE_URL=http://localhost:5173 npx playwright test
```

**6. Tear down** when you're done:

```bash
COMPOSE_FILE=docker-compose.yml:docker-compose.ci.yml docker compose down -v
```

## Debugging tips

Open UI mode for visual, step-by-step inspection:

```bash
npx playwright test --ui
```

Run a single spec:

```bash
npx playwright test tests/auth.spec.ts
```

**Inspect failed artifacts.** Playwright captures screenshots, traces, and an HTML report
on failure — check [test-results/](test-results/) for failure snapshots, or open the
report with `npx playwright show-report`.

**Stay proxy-aware.** Any new backend endpoint (e.g. custom OAuth or auth paths under
`/_allauth`) must be added to `server.proxy` in [vite.config.ts](vite.config.ts), or the
request won't be routed when running without Caddy.
